现状判断

这次升级预期能带来什么，按目前掌握的证据分三类。

范围（2026-10-13）hypersync 只负责让节点同步区块，mempool 不在范围内：下游节点不再设置 split_client_blocks，问候里的广播组为 0，节点不写 mempool_txs（每小时省约 22 GB）。下文与 mempool 相关的内容（G4、W2b、mempool 一致性、mempool 风险）仅作参考，不在关键路径上。网关现在也不带 --cache 运行：缓存占用的 6–19 GB 加上约 35 GB 的 hl-node，把主机内存推过 hl-visor 约 95% 的阈值，19 小时内导致 hl-node 重启 5 次。
预期可行

区块同步优先走 QuickNode，公共 peer 兜底。会话拆除和重新固定已在 soak 测试中验证过。bootstrap 从当前正在提供快照的 peer 转发，不依赖 sentry 的 abci_state。

已在公共 peer 上实测（现已不在范围内）

mempool（split_client_blocks = 广播组 1）经网关到达节点，--push 模式下逐字节一致、0 丢弃。仍需在 sentry 的数据流上确认。

只有 QuickNode 能回答

一个白名单 IP 能否供多个节点使用，以及每个 sentry 对单 IP 的连接数和带宽限制。这决定一份订阅能带多少节点。

集成方案：先用替身节点开发，再切换到 QuickNode

我们目前还没有 QuickNode peering。所有代码改动先针对三个公共 Hyperliquid 节点开发和测试，由它们临时充当 Tier P。到切换日再在配置中换成 sentry IP。

结论这个思路可行，但要做两点调整。分层代码从 HYPERSYNC_PRIORITY_PEERS 读取列表，所以对区块同步而言，从替身切到 sentry 只需改 .env，不需要改代码。两点调整是：挑选稳定的替身而不是随机挑；以及 mempool 在接入 QuickNode 之前无法测试，所以切换日先用 splice 模式跑一段验证，再开启 --push。

如何挑选替身

  • 挑稳定的，不要随机。从 peerd 24 小时的周期日志中，选出在至少 90% 的周期里都出现在 live_servers 中、且与 round_tip 的差距始终在 ACTIVE_ROUND_MAX_LAG 以内的 IP。随机挑的节点可能频繁上下线，替身在测试中途消失会看起来像网关 bug。
  • 确认能为我们服务。每个替身在过去 24 小时内都给网关提供过 4001 实时流和 4002 client-block 应答。
  • 分散部署。三个替身在不同的 /24 网段，最好是不同的服务商，这样对其中一个做 iptables 演练不会误伤其他。选一个靠近东京的，延迟最接近 sentry。
  • 按 sentry IP 的标准处理。只放在 .env 里，日志中显示为 prio-1..3，这样在拿到任何 sentry IP 之前，W5 就已经过真实测试。
  • 整个阶段固定不变。只有替身消失超过一天才更换，并在 soak 日志中记录。

切换日：从替身换到 sentry

  1. QuickNode 把 PUBLIC_IP 加入白名单。在 gw 网络中执行 G5，确认出口 IP。
  2. 在 .env 中把 HYPERSYNC_PRIORITY_PEERS 里的三个替身 IP 换成 sentry root。把 node1 的 reserved_peer_ips 设为同样三个。重启 peerd 和 gw，因为环境变量只在启动时读取。
  3. 按下方的切换日日志逐个查看 sentry，根据日志显示的连接上限设置 HYPERSYNC_PRIORITY_MAX_SESSIONS。
  4. 运行 24 小时，即 G3，期间记录 G4 和 G6。第一个小时用 splice 模式；当某个 sentry 上的 --push 会话在 60 秒统计行中显示 data_noround > 0 且丢弃为 0 时，再切换到 --push。
  5. 关注每 60 秒统计行中的 drop_dup、drop_floor 和 ALERT。健康会话出现非零丢弃，说明 sentry 发送了解码器会误判的帧：上线 W2b（protocol.rs 改动及其回放测试），在此之前使用 splice。
  6. 根据 G2 的数字设置 HYPERSYNC_PRIORITY_MAX_SESSIONS，然后进入阶段 4。
结果在 sentry 上做区块同步只是改配置。mempool 已不在范围内（2026-10-13），切换日不再需要 G4 和 W2b。

主网实测结果（2026-10-12）

在本机针对公共主网 peer 实测，使用临时探测、已部署的网关和一个真实节点。切换日网关会为每个 sentry 记录同样的信号（见下表），两者的差异就是 QuickNode 真正带来的变化。

发现实测带来的变化
本机 IP 必须应答 4001/4002本机没有节点监听时，所有 peer 都在不发问候的情况下关闭实时（send_abci=0）连接，peerd 排出的在线 peer 为 0。node1 发布 4001/4002 之后，同样的 peer 恢复服务。白名单 IP 上的 node1 是必需的，不是可选的：它一旦宕机，网关也会失去上游。QuickNode 教程同样要求开放入站 4001/4002。node1 要和网关一样被监控。
区块格式已变轮次从固定偏移（0x5e）移到了可变的头部位置（0x71–0xd1）。旧解码器解出 0 个轮次，导致实时 peer 审核、落后检查、缓存 floor 和 peerd 排序全部失效。已修复：轮次取第一个 0xfc R 0xfc R−1 0xfc R−2 三元组，并用一个抓取的主网区块验证。统计行新增 ALERT=no_block_rounds_decoded，下次格式变化会立即报警。
mempool = 广播组 1split_client_blocks:true 让 hl-node 的问候第 6 字节为 1。65 个在线公共 peer 中只有 8 个在该组上转发交易（每秒约 20 个数据帧和 4 个控制帧：cancelByCloid、evmRawTx 等），其余只发区块。选哪个上游决定了节点能否拿到 mempool。替身从转发交易的 peer 中挑选。QuickNode 的价值体现为 mempool 数据量。
--push 对 mempool 透明56 MB 的广播组 1 录制流经 serve_push 回放后逐字节一致，0 丢弃。经网关实时运行：转发 3,568 个区块、5,393 个数据帧和 952 个控制帧，0 丢弃。W2 的 mempool 风险已实测，而非假设。同时修复了一个相关 bug：缓存冷启动路径用广播组 0 重新问候上游，使节点悄悄降级为只收区块。
每个源 IP 2 条实时连接测试的 3 个 peer 都允许本机 IP 同时建立 2 条实时流，第 3 条在问候前被关闭。替身阶段设 HYPERSYNC_PRIORITY_MAX_SESSIONS=2。sentry 的上限由切换日的 conns 测试得出。
4002 规则没有 4001 关系时请求 client-block 区间，3 个 peer 中 2 个返回 Peer-only request。有关系时：每 100 个区块 8–10 MB，耗时 1.3–3 秒。超出 tip 的区间：client block round too large: X > tip。印证了网关为每次 4002 建立关系的设计。
只开放 4001/4002所有测试的 peer 上，4000 和 4003–4010 都被拒绝或超时。转发其他端口目前没有实际流量，保留但不要依赖。

目标架构

QuickNode 只把一个公网 IPv4 加入白名单，但允许这个 IP 建立多条 TCP 连接。这个 IP 归 hypersync 所有：只有网关会主动连接 sentry。同一 IP 上的边缘节点 node1 占用公网 4001/4002，sentry 作为 reserved peer 连入时能连到真实节点；但 node1 和其他节点一样通过网关同步。所有节点的 root_node_ips 里都只填网关。

唯一规则只有 hypersync 主动连接 QuickNode。任何节点（包括 node1）在任何阶段都不会主动连接 sentry。

青色：QuickNode 路径。只有网关主动连接 sentry；虚线表示 sentry 连入 node1，node1 只应答。琥珀色虚线：公共回退。紫色点线：peerd 探测公共池。它从不连接 sentry，sentry 的健康状况由网关在选择时自行判断。

为什么白名单 IP 上仍要有一个节点

  • sentry 会连入。reserved_peer_ips 的含义是“始终接受来自这些 IP 的入站连接”，而 QuickNode 要求白名单 IP 开放入站 4001/4002。网关从不对公网监听，所以必须由真实节点应答。这也符合 README 现有规则：公网 4001/4002 应属于真实 HL 节点。
  • 未开放 4001/4002 的 IP 会被 peer 降级。有 node1 应答，网关的出站会话就来自一个行为正常的 peer IP。
  • node1 不主动连接 QuickNode。它通过网关同步，所以 QuickNode 流量只有一个出口，监控、会话上限和故障切换都集中在一处。节点只从自己主动连接的 peer 接收数据，因此 sentry 入站连接 node1 并不会给它喂数据。
  • 从第一天起只有 hypersync 对外连接。即使是切换日的基线测量（G3、G4），node1 也接在网关后面以纯 splice 模式运行，因此没有任何其他组件会连接 QuickNode。
QuickNode 允许白名单 IP 建立多条 TCP 连接，所以 node1 技术上也可以直连 sentry。我们不这样做，是为了让每个 QuickNode 会话都经过 hypersync 的分层、会话上限和日志。QuickNode 的 verify.sh 和 verify-peer-isolation.py 假定使用其官方 compose 部署并直连 peer，因此我们改用网关日志以及 node1 的高度和 mempool 检查。

由谁应答入站 4001/4002

结论：方案 A。node1 通过 PUBLIC_IP 上的 Docker 端口映射应答。G6 用于确认 sentry 的实际行为；无论结果如何都保留 A，因为公共 peer 也会根据 PUBLIC_IP 的 4001/4002 是否应答来评价它。

方案含义结论
A. node1 端口映射Docker 把 node1 的 4001/4002 发布在 PUBLIC_IP 上。这是内核 DNAT，sentry 和其他 peer 的真实源 IP 得以保留，reserved_peer_ips 和按 IP 的限额都能正常工作。不需要改 hypersync 代码。采用
B. hypersync 转发到 node1新增一个公网监听，把入站连接透传给 node1。这样 node1 看到的所有入站连接都来自网关 IP，reserved_peer_ips 无法匹配，所有入站 peer 共用一个限速额度。否决 全面不如 A
C. hypersync 直接拒绝接受连接，回复 1 字节的“拒绝”状态帧后关闭。公网端口上不需要节点，但从不提供服务的 IP 会被 peer 降级，影响 Tier O 回退和 bootstrap。否决 即使 sentry 从不连入，也会损害 Tier O
D. hypersync 模拟节点提供 4001 数据流，并应答高度、query_peers 和 client-block 请求。高度和 query_peers 的格式尚未逆向，出错会直接影响 QuickNode。否决 工作量和风险最高
无论哪种方案，网关自身的 4000–4010 监听都保持私有。如果放到公网，网关会把 sentry 当作下游节点并为它连接上游，可能把它转回给它自己，而且任何人都能通过它拉取 4.5 GB 的 bootstrap。

端口与监听方

HL P2P 是 4000–4010 端口上的明文 TCP。帧格式为 [u32 BE 长度][类型字节][负载]：类型 0 是控制帧（问候、状态、RPC 请求），类型 1 是数据帧（状态、区块、RPC 响应）。非验证节点主要用两个端口。4001 承载 abci 流：先是 bootstrap 状态，然后是实时区块。4002 承载 gossip RPC：高度查询、query_peers 和 client-block 区间查询。

方向规则节点只从自己主动连接的 peer 接收区块。对于入站连接，节点只为对方提供服务，对方推送的内容会被忽略。所以下文所有箭头都从发起方指向监听方。下游节点必须主动连接网关，因为网关就是它的 root_node_ips。网关则总是自己向上游发起连接，任何时候都不会有连接接入节点的监听端口来给它喂数据。
端点监听谁会连接它说明
qn-1..3公网 :4001、:4002只有白名单 IP（PUBLIC_IP）。实际上只有网关。QuickNode 允许这个 IP 建立多条 TCP 连接。
公共 peer公网 :4001、:4002任何人。abci_state 按源 IP 限速。Tier O。用于 bootstrap 抓取和回退。
node1（边缘节点）PUBLIC_IP :4001、:4002，由 Docker 端口映射发布（内核 DNAT）sentry（reserved peer）和其他 HL peer必须可达，否则 peer 会降级 PUBLIC_IP。任何连回 PUBLIC_IP 的连接都落在这里，不会到 node2..N。node1 自身通过网关同步。
网关172.28.0.10 :4000–4010（私网）只有下游节点绝不对外发布。开放的网关就是 4.5 GB 的带宽放大器。
node2..N自身 :4001、:4002（不使用）没有人。try_new_peers=false，且位于私网。它们只向外连接网关。不要发布这些端口。
peerd不监听–只做出站探测和爬取。

箭头从发起方指向监听方。每条连接上的数据都是双向流动的。

代理、反向代理还是缓存

节点并不知道自己实际连的是哪个上游。它把网关当作自己的 peer 去连接，所以网关的每个监听端口都是反向代理。各通道的区别在于网关解析多少协议内容，以及是否需要连接上游。

角色位置网关做什么为什么这样设计
缓存4001 send_abci=1，缓存新鲜（≤ 8 分钟）作为源站。按 8 MB 分块写出已抓取的约 4.5 GB 数据，这次请求不建立任何上游连接。abci_state 按源 IP 限速，而网关后面的所有节点共用 PUBLIC_IP。每 4 分钟抓取一次，就能服务任意多次重启。
L4 反向代理 + 写缓存4001 send_abci=1，缓存未命中先探上游的第一帧来选上游（> 4 MB 说明对方正在提供状态），然后双向复制字节。开启 --cache 时同时把流写入缓存。状态、EVM KV 和实时区块之间的边界在线路上看不出来，只能由节点自己解析。
L4 反向代理不带 --push 的 4001 实时流；4000、4003–4010 端口splice()：两个 tokio::io::copy 循环，不做任何解析。逐字节一致，所以 split_client_blocks 的 mempool 帧原样通过。这是阶段 1 的安全模式。
L7 反向代理带 --push 的 4001 实时流读取每一帧，解码区块轮次，对照网络 tip 检查合理性和落后程度，10 秒无数据就拆除会话。比 hl-node 自身的读超时更快完成故障切换。W2 会让转发变为逐字节一致。
L7 RPC 反向代理4002读取一个请求帧，发给固定的 active。对回复分类（Peer-only request、轮次过小或过大、无 client blocks），必要时重试和对冲，最后返回一个响应。peer 只回答与自己有 4001 关系的 IP 的 4002 请求。从缓存启动的节点没有这种关系，所以由网关代为建立。
客户端缓存刷新、4002 对冲、peerd网关或 peerd 以自己的身份发起连接：抓取用 GREET_TRUE，临时关系和探测用 GREET_FALSE。不代理任何人，但这些连接同样计入 PUBLIC_IP 的限额。
内核 DNATqn-1..3 → PUBLIC_IP → node1不参与。由 Docker 端口映射转发，保留 sentry 的源 IP。sentry 作为 reserved peer 连入 node1。node1 为其服务，但只通过网关同步。
整个设计里没有正向代理。节点从不指定目的地，由网关选择。上游从不连接网关，任何连接 PUBLIC_IP 的流量都会到达 node1。

场景时序

每张图跟踪一种情况在网关中的完整过程。实线箭头是发送方发起的请求或数据流，虚线箭头是回复。颜色与架构图一致：青色 QuickNode，琥珀色公共，紫色缓存与探测，珊瑚色故障。

S1 · 冷启动，缓存命中

node2 没有本地状态。网关从自己的缓存提供快照，然后把 node2 接到一个 sentry 上接收实时区块和追块。

1–4 缓存：没有任何上游看到这次 bootstrap5–7 L7 反向代理8–11 RPC 反向代理

S2 · 冷启动，缓存未命中

缓存过期或为空。网关找到一个此刻正在提供状态的公共 peer，逐字节转发，同时写入缓存。

1–4 带首帧探测的 L4 反向代理5 写入缓存6–9 RPC 反向代理，固定在同一个公共 peer
bootstrap 连接会在同一个 socket 上直接变成实时流，所以 node2 会一直停在这个公共 peer 上，收不到 mempool，直到下一次 4001 重连。W4 的自动回切才能把它带回 Tier P。这是保持缓存新鲜的主要理由。

S3 · 在 QuickNode 上稳定运行

node2 已有状态，用 send_abci=0 重连。网关让多个 sentry 竞速并固定胜者，node2 的所有端口都跟随这个固定。

1–5 L7 或 L4 反向代理6–9 RPC 反向代理10–11 L4 透传

S4 · active 变慢或拒绝时的 4002 对冲

固定的 sentry 在 2 秒宽限期内没有响应，或者回复 Peer-only request。网关转向其他 peer 对冲，并先为每个 peer 建立临时 4001 关系。

终止性错误（如 round too large）只在全部失败时才转给节点全部失败则关闭 socket，由节点重试

S5 · sentry 故障、回退与回切

active sentry 停滞或落后。网关结束会话，node2 重连，选择流程从 Tier P 重新开始。

拆除而非热切换：新 peer 从它自己的 tip 开始发送，所以 node2 必须重新握手（commit eb52e65）

S6 · 边缘节点与 peerd

node1 和其他节点一样经网关同步，同时在公网 4001/4002 上接受 sentry 的入站连接。peerd 按自己的周期探测公共池，从不连接 sentry。

1–2 与 S3 相同3 经 Docker DNAT 入站，node1 只提供服务4 peerd 不接触 sentry

通道现状升级后原因

实时 peer 选择流程

新的 select_live_peer 流程。总预算仍为 3.5 秒（LIVE_SELECT_WAIT），所以节点的重连行为不变。

阶段 A0 – 1.5 秒

并行竞速所有健康的 Tier P sentry，按当前会话数从少到多排序。跳过已达会话上限或处于冷却期的 sentry。第一个通过审核的区块（轮次合理，且与 tip 的差距在 ACTIVE_ROUND_MAX_LAG 内）胜出。

阶段 B1.5 – 3.5 秒

沿用现有的 Tier O 竞速：在排序后的公共池上使用 4 个并行名额。会话标记为 fallback，节点继续同步区块，但收不到 mempool。

无可用 peer3.5 秒后

与现在相同：走 serve_push_4001_fallback 或关闭连接，由节点重试。

回切重连时

回退会话在下一次自然重连时回到 Tier P。可选的强制回切（默认关闭）会在某个 sentry 连续两轮 peerd 检查通过后拆除会话。

W2

保证 mempool 安全的 active 转发

W2a 阶段 2 · 约 2 天 · W2b 在切换日 G4 之后

问题

在 active 流上，pump_merge 和 process_live_frame 会让每个能解出轮次的类型 1 帧经过 RoundForwardGate。轮次小于等于 last_forwarded 的帧会被丢弃（src/protocol.rs:348），小于等于 live_floor 的也会被丢弃。

如果 split 片段带有类似区块的头部，mempool 片段就会丢失。如果片段先于所属区块到达，区块本身也可能被丢掉。新的落后保护还可能因为误解析 split 帧而拆掉健康的会话。

改动

  • W2a（已实现）：按会话统计转发的帧（控制帧、区块、无轮次数据帧）和轮次门控的丢弃数，每 60 秒及会话结束时记录，并记录前 5 次丢弃的载荷开头。转发规则不变，因为 live floor 保护着缓存冷启动路径。公共 peer 上的实测：mempool 流经 serve_push 回放后逐字节一致，实时会话转发 mempool 时 0 丢弃。
  • 轮次门控和 floor 只用于影子注入，而影子注入保持关闭。
  • W2b，G4 之后：根据抓包结果在 protocol.rs 中新增 frame_kind(payload)（Block、SplitPiece 或 Other），让健康检查只从 Block 帧读取轮次。

过渡规则

在 W2a 上线且 G4 在真实 sentry 上确认之前，QuickNode 层的会话不使用 --push。纯 splice 是逐字节透传的。网关已有这条路径，W1 为它加上层级排序。

完成标准

  • W2a：把录制的替身流送入 serve_push，输出逐字节一致（新增类似 mock 的测试夹具）。切换日再用 sentry 的录制重复一次。
  • 切换日：各节点的 mempool_txs 彼此一致且速率达到 G3 基线：6 小时窗口内节点间交易哈希重合度不低于 99.9%。该阈值为提议值，首次基线测量后再定。

W7

按 sentry 扇出（有条件）

阶段 4 · 约 1–2 周 · 仅当 soak 触及 sentry 限制时

思路

每个 sentry 只开一条上游 4001 流，把它的帧复制给分配到该 sentry 的所有节点。sentry 的负载从随节点数 N 增长变为常数。

这不是已关闭的多源合并。它是单一来源的逐字节复制，所以不存在 proposer 与分叉正确性的问题。

  • 每个 sentry 一个广播器：缓存问候帧，通过 tokio::sync::broadcast 通道发送 Arc<[u8]> 帧。
  • 节点在缓存的问候之后、从帧边界接入，缺口通过现有的 4002 代取路径补齐。
  • 慢消费者（接收端落后）会被结束会话，由节点重连。

待解决的风险

  • hl-node 是否接受问候之后从流中间开始的数据？真实的新流也是从 peer 的 tip 开始，所以大概率可行，但必须测试。
  • 只有广播器持有 peer 关系时，4002 的 Peer-only 检查是否仍能通过？所有连接共用一个 IP，这可能有帮助。
  • 多个慢节点落后时 mempool 占用的内存。

完成标准

  • N 个 fakenode 加 2 个真实节点共用 1 条 sentry 流：各节点的区块和 mempool 结果一致，且 sentry 只看到 1 条流。

上线阶段

每个阶段都以可度量的退出检查结束。任何阶段都可以单独停下，不会让系统比现在更差。

阶段 0现在 · 约 2 天

提交当前的落后保护改动。把 G1 和 G2 发给 QuickNode。选出三个替身，并对现有网关做 24 小时参照运行，记录区块时序和重启耗时。

退出替身已选定，问题已发出，参照数据已记录。
阶段 1替身，仅 splice · 约 1 周

针对替身完成 W1、W3、W5、W6。网关不带 --push 运行，保留 --cache。在 node1 之外再接入一个真实节点。

退出24 小时 soak：节点在 Tier P 上的时间 ≥ 99%，iptables 演练在 3.5 秒内回退，没有发往替身的 send_abci，日志中没有替身 IP。
阶段 2替身，push + 回切 · 约 1 周

W2a 和 W4。重新开启 --push，以获得它的停滞拆除能力。对替身进行断开再恢复的演练。

退出逐字节回放测试通过。演练中回退 ≤ 3.5 秒且回切正常。24 小时 push soak 无异常。
阶段 3切换日 · 约 2–3 天

按切换日清单执行：G5、替换 IP，然后在 splice 模式下做 G3、G4 和 G6。如果 G4 需要就上线 W2b，然后开启 --push。

退出每个节点的 mempool 达到 G3 速率，一致性 ≥ 99.9%，Tier P 驻留 ≥ 99%，日志中没有 sentry IP。
阶段 4容量 · 3 天到 2 周

在真实节点之上逐步增加 fakenode（2、4、8、16），直到出现 peer_full、吞吐瓶颈或 mempool 缺口。只有当这个上限低于所需节点数时才做 W7。

退出记录下每个 IP 可承载的节点数上限（有无扇出两种情况）。

验证与指标

指标测量方式目标
Tier P 停留率W4 中每个节点的 tier= 日志摘要≥ 99% 的会话时间
mempool 一致性每小时对比各节点 mempool_txs 中的交易哈希，并与 G3 基线速率比较重合度 ≥ 99.9%（提议值）
区块到达时差网关收到第 N 轮与各节点应用该轮的时间差，p50/p99，先与阶段 0 的参照比较，再与 G3 比较先记录基线，暂不设硬目标
回退耗时iptables 丢弃所有 sentry 流量，到第一个公共区块被转发≤ 3.5 秒选择时间加上节点重连
sentry abci 拉取统计发往优先 peer 的 send_abci:true 会话Tier O 非空时为 0
重启耗时节点重启到第一个应用区块，缓存命中不差于当前 soak 结果

风险与待确认问题

风险影响缓解措施
条款 QuickNode 不允许共用一个 IP多节点收益消失写代码前先完成 G1。退回到每个节点一份订阅，hypersync 只负责缓存和故障切换。
容量 sentry 的单 IP 限制peer_full、会话被挤到 Tier O、mempool 缺口W1 的会话上限、阶段 4 实测、W7 扇出
mempool 网关改动了 split 帧下游悄无声息地丢失 mempoolW2 之前只用 splice。逐字节回放测试。一致性指标。
回退 在公共 peer 上悄悄失去 mempool下游消费方读到过期或空的 mempoolW4 层级日志、新鲜度告警，消费方检查当前层级
限速 网关向 sentry 拉取 abci_state在最需要时被 sentry 拒绝提供状态W3 策略，且缓存刷新永不使用 Tier P
延迟 多一跳节点比直连更晚看到区块和 mempool测量网关收到区块与节点应用区块的时间差。延迟敏感的节点部署在网关主机上。
单点 所有下游节点共用一个网关网关宕机则包括 node1 在内的所有节点停滞与现在相同，但现在还会切断所有 QuickNode 流量。第二个网关需要自己的白名单 IP，或在同一主机上做热备。
node1 白名单 IP 上的 node1 宕机peer 会拒绝来自 4001/4002 不应答的 IP 的实时流，网关因此失去上游node1 的重启策略和监控与网关同级；已于 2026-10-12 实测
线格式 Hyperliquid 再次改变帧布局轮次解码失效；审核、落后检查和排序全部失效统计行中的 ALERT=no_block_rounds_decoded；每次 hl-node 升级后检查 60 秒统计行（blocks > 0、丢弃为 0）
替身 公共替身与 sentry 行为不同代码在替身上通过，切换日却出现新问题：peer_full、限速、split 帧切换日先只用 splice，执行 G3、G4 和 G6。--push 和会话上限等拿到真实数字再定。
泄露 sentry IP 通过日志或文件泄露违反 QuickNode 的保密要求W5 别名、文件权限，每次 soak 都 grep 日志
本方案尚未针对 QuickNode 实际运行过。架构依据是 QuickNode 公开的部署教程、Hyperliquid 节点 README 和 hypersync 逆向得到的协议笔记。替身现在负责验证代码路径；切换日的检查项则在开启 --push 之前验证与 QuickNode 相关的假设。
