Upgrade plan · proposed

hypersync × QuickNode peering

Use one QuickNode Hyperliquid Peering subscription as the preferred upstream for many core HL nodes. The public peer pool stays as automatic backup, and the bootstrap cache keeps restarts independent of the sentries. QuickNode allowlists a single IP, and that IP belongs to hypersync: the gateway is the only component that dials the sentries.

Where this stands

What the upgrade can be expected to deliver, split by how much evidence we have today.

Scope (2026-10-13)hypersync only has to keep nodes syncing blocks. Mempool is out of scope: downstream nodes run without split_client_blocks and greet with broadcast group 0, so the node writes no mempool_txs (~22 GB/hour saved). The mempool material below (G4, W2b, mempool parity, the mempool risks) is kept for reference only and is not on the critical path. The gateway also runs without --cache now: the cache's 6–19 GB next to a ~35 GB hl-node pushed host memory past hl-visor's ~95% threshold and caused 5 hl-node restarts in 19 h.
Expected to work

Block sync with QuickNode first and public peers as fallback. Session teardown and re-pin are already proven in soaks. Bootstrap is relayed from whichever peer is serving it, so sentry abci_state is never required.

Measured on public peers (now out of scope)

Mempool (split_client_blocks = broadcast group 1) reaches the node through the gateway, byte-identical in --push mode with 0 drops. Still to confirm on the sentries' stream.

Only QuickNode can answer

Whether one allowlisted IP may feed several nodes, and the per-IP connection and bandwidth limits on each sentry. These decide how many nodes one subscription can carry.

Integration plan: build on stand-ins, then swap in QuickNode

We have no QuickNode peering yet. Every code change is built and tested against three public Hyperliquid nodes standing in as Tier P. On swap day the sentry IPs replace them in config.

VerdictThe approach works, with two adjustments. The tier code reads its list from HYPERSYNC_PRIORITY_PEERS, so for block sync the move from stand-ins to sentries is an .env change, not a code change. The adjustments: pick stable stand-ins instead of random ones, and accept that mempool cannot be tested before QuickNode, so swap day starts in splice mode with a short verification run before --push is turned on.

Choosing the stand-ins

  • Stable, not random. From 24 h of peerd cycle logs, take IPs that are in live_servers in at least 90% of cycles and stay within ACTIVE_ROUND_MAX_LAG of round_tip. A random pick may churn, and a stand-in that vanishes mid-test looks like a gateway bug.
  • Proven to serve us. Each one has given the gateway both a 4001 live stream and a 4002 client-block answer in the last 24 h.
  • Spread out. Three different /24s, ideally three providers, so an iptables drill on one does not hit the others. One near Tokyo gets latency closest to the sentries.
  • Handled like sentry IPs. Kept only in .env and labeled prio-1..3 in logs, so W5 is tested for real before any sentry IP exists.
  • Pinned for the whole phase. Replace a stand-in only after it has been gone for a day, and note the swap in the soak log.

Swap day: stand-ins to sentries

  1. QuickNode allowlists PUBLIC_IP. Run G5 from the gw network to confirm egress.
  2. In .env, replace the three stand-in IPs in HYPERSYNC_PRIORITY_PEERS with the sentry roots. Set node1's reserved_peer_ips to the same three. Restart peerd and gw, since env is read at start.
  3. Read the swap-day log lines below for each sentry. Set HYPERSYNC_PRIORITY_MAX_SESSIONS from the connection cap they show.
  4. Run 24 h. This is G3, with G4 and G6 logged during it. Start in splice mode for the first hour; switch to --push once a --push session on a sentry shows data_noround > 0 and zero drops in its 60 s stats lines.
  5. Watch drop_dup, drop_floor and ALERT in the 60 s stats lines. Non-zero drops on a healthy session mean the sentries send frames the decoder misreads: ship W2b (a protocol.rs change and its replay test) and use splice until then.
  6. Set HYPERSYNC_PRIORITY_MAX_SESSIONS from G2's numbers, then start Phase 4.
ResultBlock sync on the sentries is a config change. Mempool is out of scope (2026-10-13), so G4 and W2b are no longer needed for swap day.

Send the G1 and G2 questions to QuickNode now, before buying: G1 decides whether one IP may feed several nodes at all. Coding does not wait for the answer, because W1–W6 also help with one QuickNode node, or with none.

Target architecture

QuickNode allowlists one public IPv4 and accepts several TCP connections from it. That IP is hypersync's: the gateway is the only component that dials the sentries. An edge node (node1) on the same IP owns public 4001/4002, so sentries connecting in as reserved peers reach a real node, but node1 syncs through the gateway like every other node. All nodes list only the gateway in root_node_ips.

One ruleOnly hypersync connects out to QuickNode. No node, node1 included, ever opens a connection to a sentry, in any phase.

Teal: QuickNode path. Only the gateway connects out to the sentries; the dashed arrow is the sentries connecting in to node1, which only answers. Amber dashed: public fallback. Violet dotted: peerd probes the public pool. It never dials the sentries; the gateway judges their health during selection.

Why keep a node on the allowlisted IP

  • Sentries connect in. reserved_peer_ips means "always accept inbound from these IPs", and QuickNode requires inbound 4001/4002 open on the allowlisted IP. The gateway never listens publicly, so a real node has to answer there. This matches the README rule that public 4001/4002 belong to a real HL node.
  • Peers deprioritize IPs without open 4001/4002. With node1 answering, the gateway's outbound sessions come from an IP that behaves like a normal peer.
  • node1 does not dial QuickNode. It syncs through the gateway, so QuickNode traffic has one owner and one place to monitor, cap and fail over. A node only ingests from peers it dials, so the sentries' inbound connections to node1 do not feed it.
  • Only hypersync connects out, from day one. Even the swap-day baseline (G3, G4) runs node1 behind the gateway in plain splice mode, so no other component ever opens a connection to QuickNode.
QuickNode accepts several TCP connections from the allowlisted IP, so node1 could dial the sentries directly. We don't, so that every QuickNode session goes through hypersync's tiers, session caps and logs. QuickNode's verify.sh and verify-peer-isolation.py assume their own compose setup and a direct peer, so we replace them with gateway logs plus node1's height and mempool checks.

Ports and listeners

HL P2P is plain TCP on ports 4000–4010. Frames are [u32 BE length][type byte][payload]: type 0 is control (greeting, status, RPC request) and type 1 is data (state, blocks, RPC responses). Two ports matter for a non-validator. 4001 carries the abci stream: bootstrap state, then live blocks. 4002 carries gossip RPC: height, query_peers and client-block range queries.

Direction ruleA node ingests blocks only from peers it dials. On an inbound connection it serves the dialer and ignores anything pushed at it. So every arrow below points from the dialer to the listener. A downstream node must dial the gateway, because the gateway is its root_node_ips entry. The gateway in turn always dials upstream itself, and nothing ever connects into a node's listener to feed it.

Proxy, reverse proxy or cache

The node never knows which upstream it is talking to. It dials the gateway as if the gateway were its peer, which makes every gateway listener a reverse proxy. What changes per channel is how much of the protocol the gateway reads, and whether it contacts an upstream at all.

The bootstrap connection turns into the live stream on the same socket, so node2 stays on that public peer, without mempool, until its next 4001 reconnect. W4 fail-back is what brings it back to Tier P. This is the main reason to keep the cache warm.

S3 · Steady state on QuickNode

node2 already has state and reconnects with send_abci=0. The gateway races the sentries and pins the winner, and all of node2's ports follow that pin.

S4 · 4002 hedge when the active is slow or refuses

The pinned sentry does not answer within its 2 s grace period, or answers Peer-only request. The gateway hedges across other peers, giving each one a temporary 4001 relationship first.

The active sentry stalls or falls behind. The gateway ends the session, node2 reconnects, and selection starts again from Tier P.

S6 · Edge node and peerd

node1 syncs through the gateway like any other node, and also accepts the sentries' inbound connections on public 4001/4002. peerd probes the public pool on its own schedule and never dials the sentries.

Live peer selection ladder

The new select_live_peer flow. It keeps the existing 3.5 s total budget (LIVE_SELECT_WAIT) so node reconnect behaviour does not change.

Stage A0 – 1.5 s

Race all healthy Tier P sentries in parallel, ordered by fewest active sessions. Skip any sentry at its session cap or in cooldown. First vetted block (plausible round, within ACTIVE_ROUND_MAX_LAG of the tip) wins.

Stage B1.5 – 3.5 s

The existing Tier O race: 4 parallel slots over the ranked public pool. The session is tagged fallback, and the node keeps syncing blocks but loses mempool.

No peerafter 3.5 s

Same as today: serve_push_4001_fallback or close, and the node retries.

Fail-backon reconnect

A fallback session returns to Tier P at its next natural reconnect. Optional forced fail-back (off by default) tears the session down once a sentry has passed two consecutive peerd cycles.

Work items

Each item lists the change, the code it touches, and how we know it is done. Effort figures are rough engineer-day estimates.

W1

Upstream tiers (priority peers)

Phase 1 · built 2026-10-12

Change

  • New module priority.rs. Gateway and peerd both read HYPERSYNC_PRIORITY_PEERS. peerd excludes those IPs from discovery, probing and peers.json, like HL_SELF_IP. The gateway strips them from the pool it reads, so Tier O never contains them.
  • Tier P health is judged in the gateway itself: a failed attempt (refused, peer full, lagged, no block) puts the peer in a 30 s cooldown. Sessions are counted per peer, and the least-loaded peer is tried first.
  • select_live_peer becomes the two-stage ladder above. Per-sentry session counters (HashMap<String, AtomicUsize> in GatewayCtx) are incremented on pin and decremented on clear_active_if_current.
  • The non-push splice loop in handle_4001_live and client_block_peer_candidates iterate Tier P before the pool.

Done when

  • fakenode ×3 with 3 stand-ins: each lands on a different one.
  • Block one stand-in with iptables: its node re-pins to another within one reconnect. Block all three: nodes go to Tier O within 3.5 s.
  • With HYPERSYNC_PRIORITY_PEERS unset, the existing tests and soak behave the same as before.

W2

Mempool-safe active forwarding

W2a Phase 2 · ~2 d · W2b on swap day, after G4

Problem

On the active stream, pump_merge and process_live_frame pass every type-1 frame with a decodable round through RoundForwardGate. Rounds at or below last_forwarded are dropped (src/protocol.rs:348), and so are rounds at or below live_floor.

If split pieces carry a block-like header, mempool pieces are lost. If they arrive before their block, the block itself may be dropped. The new lag guard can also tear down a healthy session on a misparsed split frame.

Change

  • W2a (built): per-session counts of forwarded frames by kind (control, block, round-less data) and of round-gate drops, logged every 60 s and at session end, with the first 5 drops logged with their payload head. The forwarding rules are unchanged, since the live floor protects the cache cold-start path. Measured on public peers: a mempool stream replayed through serve_push came out byte-identical, and live sessions forward mempool with 0 drops.
  • The round gate and floor apply only to shadow injection, which stays disabled.
  • W2b, after G4: add frame_kind(payload) in protocol.rs from the pcap findings (Block, SplitPiece or Other), so the health checks read rounds only from Block frames.

Interim rule

Until W2a ships and G4 confirms it on the real sentries, run QuickNode-tier sessions without --push. Plain splice is byte-transparent. The gateway already has this path; W1 adds tier ordering to it.

Done when

  • W2a: a recorded stand-in stream fed through serve_push comes out byte-identical (new mock-style fixture). On swap day, repeat with a sentry recording.
  • Swap day: every node's mempool_txs matches the others and reaches the G3 baseline rate: at least 99.9% tx-hash overlap between nodes over a 6 h window. The threshold is a proposal, to be set after the first baseline.
  • Swap day: no lagged teardowns caused by split frames in a 24 h soak.

W7

Per-sentry fan-out (conditional)

Phase 4 · ~1–2 wk · only if the soak hits sentry limits

Idea

Open one upstream 4001 stream per sentry and copy its frames to every node assigned to that sentry. Sentry load becomes constant instead of growing with N nodes.

This is not the disabled multi-source merge. It is one source copied byte-for-byte, so the proposer and fork concern does not apply.

  • A broadcaster per sentry caches the greeting frame and sends Arc<[u8]> frames over a tokio::sync::broadcast channel.
  • A node joins at a frame boundary after the cached greeting and fills its gap through the existing 4002 fetch-forward path.
  • A slow consumer (a lagged receiver) has its session ended, and the node reconnects.

Open risks

  • Does hl-node accept a stream that starts mid-flow after the greeting? Real fresh streams start at the peer's tip, so this is probably fine, but it must be tested.
  • Does 4002 Peer-only still pass when only the broadcaster holds the relationship? All connections share one IP, which probably helps.
  • Mempool memory when several slow nodes lag behind.

Done when

  • N fakenodes plus 2 real nodes on 1 sentry stream: identical block and mempool results across nodes, and the sentry sees 1 stream.
